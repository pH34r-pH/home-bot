# Pixel streaming voice and bounded listening — experiment 01

Tested October 21, 2026 on the physical Pixel 5 running Android 14, through
authorized USB ADB. The keyguard remained locked. These are Android device tests,
separate from Webots. No robot motion or command dispatch was connected.

**Result:** native streaming Phonon playback, playback cancellation, real microphone
capture, and sherpa-onnx WAV recognition work. PC-to-Pixel acoustic recognition
recovered only partial words at the louder setting. It is not ready for reliable
verbal control.

## Runtime and model

- Phonon: upstream `xn-ptts` v0.4.0, source
  `f07d7952db0c6127d5e4bc3f41c82b3304b6b5aa`, q8 English 31M checkpoint,
  two CPU threads. The [earlier report](../phonon-native-01/README.md) records its
  exact model revision/digests and generation-only benchmarks.
- ASR: official [sherpa-onnx 1.13.8 Android AAR](https://github.com/k2-fsa/sherpa-onnx/releases/tag/v1.13.8),
  C API through a small C/JNI adapter; bundled ONNX Runtime, CPU provider,
  two threads, greedy search, 80-bin features at 16 kHz.
- Model: [20M English streaming Zipformer, 2023-02-17](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/online-transducer/zipformer-transducer-models.html),
  int8 encoder/joiner, float decoder, tokens file: 45,202,074 bytes total.
  Its package README and [source model card](https://huggingface.co/desh2608/icefall-asr-librispeech-pruned-transducer-stateless7-streaming-small)
  declare Apache-2.0. Sherpa-onnx is Apache-2.0;
  [ONNX Runtime is MIT](https://github.com/microsoft/onnxruntime/blob/main/LICENSE).
- [Asset manifest](assets.json) records download URLs and SHA-256 checksums.
  `scripts/prepare_sherpa.py` verifies them. No model/binary is committed.

## Streaming playback

JNI passes each generated float PCM block into a bounded two-block queue. A
separate writer feeds Android AudioTrack in at most 80 ms writes. It waits for
400 ms of ready PCM before starting, because the CPU runtime can emit a small
initial block followed by a much larger batch. Playback and synthesis overlap.
The app loads the model anew for each test; this is not a persistent warmed engine.

The 7.52 second [known utterance](../phonon-native-01/pixel-generated.wav) said:

> Hello. I am your home robot. My voice is running directly on this Pixel phone.
> Please turn left, then stop.

| Measurement | Observed |
| --- | --- |
| First JNI PCM callback, from service worker start | 861 ms |
| First played frame observed by a 10 ms polling thread | 1,898 ms |
| Entire service playback | 9,353 ms |
| Queued / played samples | 180,480 / 180,480 at 24 kHz |
| AudioTrack underruns | 0 |
| Output route | Built-in speaker |
| Keyguard | Locked |

See [stream metrics](stream-final.json). An earlier buffered run started playing
at 2,541 ms and also reported zero underruns. These are frame-progress measurements,
not microphone measurements of first audible sound, and are not generation-only
speed figures. Cold-start latency varies. The initial unbuffered implementation
had an underrun and was replaced before these results were recorded.

In the [cancellation test](stream-cancel.json), ADB requested STOP at 3,606 ms,
after playback began. AudioTrack paused at 31,680 played frames; its final count
was 32,640, another 40 ms of frame progress. The service finished native generator
cleanup at 4,767 ms and reported `cancelled`. Playback stop and generator cleanup
are separate events; this is not an emergency motion-stop measurement.

Playback temporarily used media volume 6/25 and half track gain, then restored
the original 0/25 setting. No speech service or Home Bot wake lock remained active
after the tests. The final installed build also passed a shorter streaming test;
see [short stream metrics](stream-short.json).

The files were generated by Phonon on the Pixel. The app decoded them on the Pixel,
without a microphone or network. These validate the model path, not acoustics.
Input WAVs are 24 kHz; sherpa-onnx resamples to its 16 kHz feature rate internally.

## Microphone and PC acoustic tests

The explicitly started foreground microphone session uses the built-in microphone,
`VOICE_RECOGNITION`, 16 kHz mono PCM16, and a fixed capture window. Android reported
`client_silenced: false` and recording state 3. A [five-second quiet baseline](microphone-baseline.json)
captured 80,000 samples (RMS 0.000545, peak 0.00256) and returned empty text.
Raw microphone audio was never saved or uploaded.

For each acoustic attempt, the host waited until the phone reported `listening`,
then used `ffplay -nodisp -autoexit` to play a known synthetic fixture through the
PC's current output. All PC player processes exited successfully. The default
Windows endpoint identified itself as **Headphones (Realtek USB Audio)**, unmuted,
with original system volume 10%. Its physical location/output arrangement was not
confirmed, so these are observations of this setup, not an ASR accuracy benchmark.

| Attempt | Fixture / PC settings | Microphone RMS / peak | Transcript |
| --- | --- | --- | --- |
| [1](pc-acoustic-01.json) | Long utterance; system 10%, ffplay 70% | 0.000620 / 0.00342 | Empty |
| [2](pc-acoustic-02.json) | Long utterance; system 25%, ffplay 70% | 0.001410 / 0.00903 | Empty |
| [3](pc-acoustic-03.json) | Short command; system 50%, ffplay 100% | 0.003104 / 0.02686 | `T THEN STOPPED` |

The last transcript is consistent with partial pickup of the known command.
It does **not** recover the full command. PC volume was restored to its original
10% after each adjusted-volume test; phone volume remained 0/25 while listening.
There were no wake-word, speaker identity, background speech, distance, noise,
or false-activation evaluations. A single empty silence window establishes none
of those rates.

## Follow-up: delayed playback and wider capture windows

At the owner's request, the PC tests were repeated with a two-second delay after
the host observed `listening`. Playback additionally waited for at least 32,000
microphone samples (two seconds at 16 kHz), rather than relying only on service
startup. The short clip used a 16-second capture and the long clip used 20 seconds.
PC endpoint, fixture and gain settings matched their corresponding earlier runs.

| Retry | Clip | Launch after listening observed | Captured samples at launch | PC exit before completion observed | Transcript |
| --- | --- | --- | --- | --- | --- |
| [Short delayed](pc-acoustic-04-delayed.json) | 2.56 s; system 50%, ffplay 100% | 2,047 ms | 32,000 | 11,313 ms | `T THEN STOPPED` |
| [Long delayed](pc-acoustic-05-delayed.json) | 7.52 s; system 25%, ffplay 70% | 2,078 ms | 32,000 | 10,282 ms | Empty |

The PC player ran for approximately 2.83 and 7.72 seconds, respectively. The Pixel
captured all 256,000 / 320,000 requested samples, remained locked, and Android
reported neither session silenced. Host observation timestamps include polling
and reporting latency; they are not sample-synchronized timestamps. The large
leading/trailing margins enclose both clips without relying on precise clock
alignment. Both results match the corresponding earlier transcripts, so simply
starting PC playback too early or ending capture too soon does not explain these
failures. This does not isolate the remaining acoustic/model error.

`phone_speech.py listen --play-wav` now defaults to this two-second delay and a
four-second trailing budget. It automatically expands capture to fit the fixture,
both margins, and two seconds of host launch/report allowance, rejects clips that
cannot fit the 30-second app limit, and checks the observed trailing margin.
Three scheduling regression tests were added; all 19 Python tests passed.
PC volume was restored to 10%, phone volume stayed 0/25, and the speech service
was stopped afterward. No raw microphone audio was retained.

## Reproduce and next work

Build/install and usage are in the [native speech README](../../../android/speech-native/README.md).
`phone_speech.py` supports `speak`, bounded `listen`, and `file`, plus optional PC
fixture playback and streaming cancellation. Reports/transcripts stay in ignored
local artifacts until explicitly selected for this report. Only known synthetic
text and empty/fixture-related transcripts are included here.

Confirm speaker/phone placement and input levels, then compare a stronger streaming
ASR model on the same fixtures. Improve clean-file accuracy before treating any
recognized phrase as an intent. A later robot harness will need endpointing,
turn-taking, echo handling and an explicit final-transcript-to-intent boundary.
There is currently no MCP speech interface or actuator dispatch. No S23 test,
camera concurrency, full-duplex conversation, battery endurance, or household
autonomy is validated by this experiment.

Android Java/C/JNI compilation and APK signature verification passed. The existing
16 Python control/API tests passed. Those tests do not validate Android audio;
the device evidence above does.
